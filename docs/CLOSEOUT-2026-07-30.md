## §2 — Follow-up 1: the 77.26 provenance, checked and confirmed

**The question, stated narrowly enough to fail:** is the notebook's mean pLDDT of 77.26 computed
live from the fold's per-residue array, or read from a stored value that happens to be 77.26? The
first is reproduction. The second is reading one number twice and calling it agreement.

**How known (D-016):** `notebooks/miniature_NECTIN4.ipynb` inspected on the box 2026-07-30, plus a
live `GET https://pharmfoldmdk.fly.dev/api/analyses`.

- `77.26` appears **exactly twice** in the notebook, both times in **output** streams (cell 7 stdout,
  cell 12 stdout). **Zero occurrences in any source cell** — checked by parsing the notebook JSON and
  testing every cell's `source` array for the literal, not by reading line numbers, because a line
  number cannot distinguish source from output.
- **Cell 7 computes it live:** `sum(plddt)/len(plddt)` over `result.plddt`, returned by
  `worker.runner.fold(...)` — a real in-session fold, with `fold_seconds` measured off `time.time()`.
- **Cell 12's `mean_plddt_ecd = 77.26334929466248`** comes from `result.provenance.mean_plddt` — the
  runner's own mean over that same live array. A second computation path over the same fold; they
  agree.
- **The notebook touches the deployed app exactly once** — cell 16, `/api/ranking`, for score and
  rank only, explicitly labelled *"loaded, not re-fitted."* **It never reads a stored `mean_plddt`.**
  There is no path by which the deployed value could have leaked into the printed one.
- **The deployed value, fetched independently today:** NECTIN4 `mean_plddt` **77.26**, `disposition`
  `ranked`, `boundary_method` `sliced_ecd`, `tier` `local`.

**Verdict: reproduction confirmed.** A live fold and the stored fold are two independent
computations that agree.

**The honest limit, stated because it will occur to a grader before it occurs to us:** the notebook
*prints* its live number; it does not *assert* the match. The comparison to the deployed value is
performed by a reader, here and in the log — not by the artifact. Making it self-evidencing means
cell 19's promise-checklist fetching the stored mean and asserting equality. **Not done, deliberately
left as a decision for the owner** — the notebook is already committed and delivery is imminent.

`intersection_check.py` had been sitting untracked at the repo root since 2026-07-27. The obvious
resolutions — delete it, or move it — were both wrong, for two different reasons.

**It could not be deleted.** F-002 and the log both cite it **by path** as their D-016 provenance

inside the mechanism built to prevent it. The commit had been deferred on an explicit condition
(*"do not commit until the D-058 features PR is merged and green"*), and **that condition was
discharged**: D-058 is `73c0742` (PR #85), contained in `main`.

**It could not simply be moved either — and this is the part worth reading.** Running it before
touching it reproduced **both errors F-002 recorded against it on 2026-07-27 and never closed in
the file**. Today, as handed over, it printed `80 folded` and `13 of 80 = 16.2%` — **contradicting
F-002's `79` and `15.2%`, in the same repository.**

1. **`/api/analyses` is the ENQUEUED set, not the folded set.** `core/enqueue.py` writes a
   `protein_analyses` row at *enqueue* time; report A printed that row count under the label
   *"folded."* The folded set is now taken from `/api/coverage` per-row `fold_status` (the D-038

## §4 — Scope note: why an instrument fix was in scope for a file move

The brief was *resolve the stray*. Fixing two errors inside it is more than that, and the judgment
should be visible rather than assumed:

- The correction had **no design freedom** — F-002 specifies both errors and both right answers.
  Nothing was invented; the log was implemented.
- The alternative was worse than doing nothing. Tracking it unfixed would **enshrine** an
  instrument that prints a number the project's own log says is wrong, at a path the log advertises
  as authoritative. Leaving it untracked leaves the citation dangling. There was no
  do-less-and-be-safe option.
- **Nothing downstream moved.** F-002's numbers are unchanged; only the instrument changed, and it
  now agrees with them. No recorded finding was revised by this work.

## §5 — The method lesson: a finding recorded against a tool is not a finding closed

This project's central discipline is *the log leads the code*, and it works. Today exposed its blind
spot.

**F-002 did everything right.** It found two real errors in its own instrument, recorded them before
the numbers, explained why they change how the numbers read, and reported the corrected figures. The
log is exemplary on this. **And the file went on printing the wrong numbers for three days**, at a
path the log described as its provenance source, one commit away from becoming the tracked
definition of the project's ranking denominators.

The gap: **for a claim, recording it in the log *is* closing it — the log is where claims live. For
a tool, recording a finding against it is only half.** A tool's home is the tool. A finding written
about a tool and not into it converts the log from a record into a trap: the next reader finds a
tracked script at a cited path, runs it, and gets numbers the log contradicts — with no marker on
the file saying so.

**The rule this suggests, offered for the log if the owner agrees:** *when a finding is against an
instrument, it is not closed until the instrument no longer exhibits it — or the instrument carries,
in itself, the statement of what it gets wrong.* The second is acceptable and sometimes the only
option; silence in the file is not. Related to F-001's lesson (a metric can be real, well-defined,
correctly queried and still measure the wrong thing) but distinct: **F-001 is about trusting an
instrument's output; this is about the instrument drifting from its own written record.**

This is deliberately **not** filed as an F-NNN entry — it is a proposal, and the Planner should rule
on whether it earns a number.

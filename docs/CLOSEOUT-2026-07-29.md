## §1 — The through-line: measure, do not reason

The day's findings share a shape: **each came from asking a question whose answer could disqualify a
plausible belief, rather than trusting the belief.** Five of them, and none was found by reasoning.

1. **The zero-positive fit (D-064).** The fit driver read a label schema the curated file never
   adopted, so *no* target counted as a positive. The empty fit raised, and the raise read as a
   *finding about the data* — a sophisticated-looking "the structure does not separate the classes."
   It was an artifact of a broken join. Found only by comparing two paths to the label count instead
   of trusting the one the driver used.

2. **The glossary guard, narrower than its name.** The 07-26 closeout claimed *"every acronym a reader
   meets is decodable."* Measured mechanically, the guard polices a **curated 13-term watchlist on 4
   scanned surfaces** — not every acronym, not every surface. The claim was narrowed to what the guard
   proves (closeout correction, appended not edited).

3. **The readability tripwire, narrower than its name.** It measures Flesch–Kincaid over **Story +
   AdcContext only** — two surfaces — not "the narrative." Discovered while flagging that D-068's new
   TargetView prose is unmeasured for legibility.

4. **The two-surface precedence disagreement (TMEM108).** A folded, held-out, below-floor target read
   *below_floor* on its target page and *held_out* on the Scorer excluded-set — one target, two
   surfaces, two reasons. Found by the partition assertion, which exists precisely to compare the two
   classifiers rather than trust either.

5. **The torch discrepancy (F-007).** `worker/requirements.txt` pins `torch 2.11.0+cu128`; the one
   captured fold recorded `torch 2.8.0+cu128`. The rental pod ran a different build than the manifest
   pins. Found by asking *"does environment capture actually work, and what did it capture?"* rather
   than trusting that a green provenance panel meant a correct one.

**The pattern to carry forward:** a plausible answer is not a measured one. Every one of these was a
belief the code invited us to hold, and every one was wrong or incomplete when a disqualifying query
was actually run. *"Prefer the query whose answer could disqualify you"* (D-016) earned its place five
times today.

## §2 — The episode that matters for Friday (D-064), in full

An early scorer run fit on zero positives. The driver joined labels on a field the curated file did
not carry, so the Group B count came back zero. With no positives, the penalized fit's Hessian is
singular for the same reason quasi-complete separation makes it singular — **the failure signature of
a meaningless input is identical to the failure signature of a hard-but-real one.** The raise was
first read as the second. That reading was withdrawn, the defect (a second label path that was never
compared to the first) was fixed by deletion not repair, and — the part that matters — **the invalid
run was kept and marked, not overwritten.** `ranking_results` id=1 still carries its `status_detail`.

Why this is the Friday headline and not a footnote: a grader has seen a hundred projects that report a
clean result. Almost none can show the moment they produced a *wrong* clean-looking result and caught
themselves. The corrected run (F-004: modest above-chance, indistinguishable from the comparator, not
a proxy for it) is a fine result. **The audit trail from artifact to correction is a better one**, and
it is legible on the Story surface in a plain, non-triumphal register.

## §5 — "Two paths to one quantity," the class, now nine deep

The project's most persistent failure mode is two independent paths to the same quantity that are
never compared, agreeing by coincidence until they don't. Today added instances and, notably, one
that was not about code:

- **F-002** — `ranked` counted two ways, sharing the value 67 (coincidence concealed it).
- **D-066** — `ranked` naming the D-024 disposition and the ranking's membership; lexical, not
  computational.
- **D-064** — two label paths, one returning zero positives (the fifth instance in a day when named).
- **The below-floor arithmetic** — *the eighth, and the first where the two paths were the Planner's
  own reasoning at two different times* (an expectation computed under the old precedence, applied to a
  set the new precedence had re-sorted).
- **TMEM108 (the ninth)** — the UI `targetStatus` and the backend `_exclusion_reason` disagreeing on a
  held-out-below-floor target's status. Closed today by realigning the UI (held_out precedes
  below_floor, pLDDT-independent) and pinning **both** implementations with partition tests — the JS
  test locks one side, the Python test proves the other agrees, so they cannot drift.

**The lesson the class keeps teaching:** when a number or a status can be computed two ways, compute it
both ways and assert they match, or you are trusting a coincidence.

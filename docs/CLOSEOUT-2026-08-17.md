## §5 — ⚠⚠ The production database was destroyed, and recovered

**What happened.** `tests/test_queue_postgres.py` was run with `.env` sourced. Its `pg_engine`
fixture opens **every test** with:

```sql
TRUNCATE TABLE jobs, protein_analyses, ranking_runs RESTART IDENTITY CASCADE
```

**`protein_analyses`: 2,771 → 1. `jobs`: 2,771 → 1.** Sequences reset.

**Why the guard did not fire.** The fixture skips *unless* `DATABASE_URL` names a reachable
Postgres. ⚠ **Supplying production credentials is precisely what disarms it.** The rule *"no
hand-written SQL against production"* was being applied to `SELECT` statements while a **test suite**
was treated as inherently safe.

**Recovery.** Fold artifacts were never touched — **2,770 directories, 455 MB, on the Fly volume**.
A safety backup of the truncated state was taken first, then
`backup_1786963963_0ac3305bbc82d7f5` (10:54Z, pre-truncate) was restored **into a new cluster**
(`zp2wjrej9lwodn4q`), verified at **2,771 / 2,771 / 2,769 complete / 5 ranking runs**, and attached.
**No fold was lost.**

⚠ **A step that nearly produced a false conclusion:** after attaching, the API still returned **0
rows**. `DATABASE_URL` was **`Staged`, not `Deployed`** — a machine restart does not apply staged
secrets, so the app kept the old connection string and answered `0` instead of erroring. **The most
misleading possible response.** `fly secrets deploy` was the missing step.

**The lesson, stated narrowly:** ⚠⚠ **`.env` in a shell is production credentials, and a test suite
is entitled to assume its database is disposable. Those two facts must never meet.**

⚠ **The recovery worked on backups nobody had verified existed.** That is luck standing in for
process, and it should not be filed as a success.
